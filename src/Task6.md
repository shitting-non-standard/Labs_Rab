# Лабораторная работа: менеджер политик анонимизации

# Вариант 6

## Общая идея

Разработать консольное приложение для подготовки текстовых файлов к безопасной передаче другим людям.

Программа должна находить в документах конфиденциальные данные и создавать анонимизированные копии, в которых найденные значения удалены, замаскированы или заменены на нейтральные обозначения.

Правила обработки объединяются в именованные политики. Пользователь может создавать отдельные политики для разных видов данных, а затем составлять из них более строгие политики.

Например:

* политика `personal-data` скрывает имена, адреса электронной почты и телефоны;
* политика `credentials` скрывает пароли, токены и ключи доступа;
* политика `network-data` скрывает IP-адреса и имена внутренних узлов;
* политика `strict` объединяет все перечисленные политики.

Программа не должна изменять исходные файлы. Результат всегда сохраняется отдельно.

---

# 1. Работа с приложением

Приложение должно управляться через текстовые команды или меню.

Пользователь должен иметь возможность:

* просматривать доступные политики и их правила;
* создавать, изменять и удалять политики;
* составлять новую политику из существующих;
* проверять политики на корректность;
* выбирать отдельный файл или каталог;
* предварительно просматривать найденные данные;
* применять выбранную политику;
* просматривать итоговый отчёт;
* перезагружать конфигурацию;
* завершать работу.

Пример командного интерфейса:

```text
> policies
> show-policy personal-data
> create-policy
> compose-policy strict
> validate-policy strict
> preview strict application.log
> anonymize strict application.log
> report
> reload
> exit
```

Разрешается реализовать нумерованное меню.

Типичный сценарий работы:

1. Пользователь выбирает файл или каталог.
2. Выбирает подходящую политику.
3. Программа анализирует содержимое и показывает количество найденных значений каждого типа.
4. Пользователь просматривает предполагаемые замены.
5. После подтверждения программа создаёт анонимизированные копии.
6. Пользователь получает отчёт о выполненной обработке.

# 2. Политики и правила анонимизации

Конфигурационный файл должен содержать одну или несколько именованных политик.

Каждая политика состоит из правил анонимизации. Для правила необходимо задавать как минимум:

* уникальное имя;
* описание;
* способ поиска данных;
* способ замены;
* приоритет;
* признак активности.

Программа должна поддерживать следующие способы поиска:

* точное текстовое значение;
* регулярное выражение;
* список значений из словаря;
* один из встроенных типов данных.

Минимальный набор встроенных типов:

* адрес электронной почты;
* номер телефона;
* IPv4-адрес;
* URL;
* значение параметра, похожего на пароль;
* токен или ключ доступа.

Имена людей, названия организаций и другие значения, которые невозможно надёжно определить по формату, должны задаваться пользователем через словарь или отдельные правила.

Пример правила:

```json
{
  "id": "emails",
  "description": "Адреса электронной почты",
  "matcher": {
    "type": "builtin",
    "value": "email"
  },
  "replacement": {
    "type": "pseudonym",
    "template": "user{number}@example.com"
  },
  "priority": 100,
  "enabled": true
}
```

---

# 3. Способы замены

Для найденных значений должны поддерживаться как минимум следующие способы обработки:

* замена постоянной строкой;
* удаление;
* частичное маскирование;
* замена последовательными псевдонимами;
* замена значением из заданного списка.

Примеры:

```text
alexey.petrov@company.ru
→ user1@example.com

maria.ivanova@company.ru
→ user2@example.com

+7 999 123-45-67
→ +7 *** ***-**-**

password=secret123
→ password=[REDACTED]

192.168.10.24
→ host1
```

При использовании псевдонимов одинаковые исходные значения в рамках одной операции должны заменяться одинаково:

```text
alexey.petrov@company.ru → user1@example.com
alexey.petrov@company.ru → user1@example.com
```

Разные исходные значения должны получать разные псевдонимы.

Связь между исходными значениями и псевдонимами не должна сохраняться после завершения операции, если это отдельно не предусмотрено конфигурацией.

# 4. Составление политик

Пользователь должен иметь возможность создать составную политику из нескольких существующих политик.

Пример:

```text
Политика strict включает:

1. personal-data
2. credentials
3. network-data
```

Составная политика не должна копировать правила вручную. Она должна хранить ссылки на включённые политики.

Допускается включать в составную политику другие составные политики.

Перед использованием программа должна раскрыть все вложенные политики и получить итоговый набор правил.

Необходимо обнаруживать циклические зависимости:

```text
policy-a включает policy-b
policy-b включает policy-c
policy-c включает policy-a
```

Такая конфигурация является некорректной.

Если несколько включённых политик содержат правила с одинаковым идентификатором, правило из политики, указанной позже, должно заменять предыдущее. Программа должна сообщить пользователю о таком переопределении.

Пример:

```text
Политика strict:

1. personal-data
2. public-demo

Правило emails из политики public-demo
переопределяет правило emails из personal-data.
```

Это позволяет использовать одну базовую политику, но изменять отдельные способы замены.

Например, обычная политика может заменять разные адреса разными псевдонимами:

```text
user1@example.com
user2@example.com
```

Более строгая политика может переопределить это правило и заменять все адреса одной строкой:

```text
[EMAIL]
```

# 5. Порядок применения правил

Все совпадения должны сначала определяться в исходном тексте, и только после этого программа должна выполнять замены.

Это необходимо, чтобы результат одного правила случайно не стал входными данными для другого правила.

Если несколько правил нашли пересекающиеся участки текста, необходимо выбрать одно совпадение.

Приоритет определяется следующим образом:

1. Побеждает правило с большим значением `priority`.
2. При одинаковом приоритете выбирается более длинное совпадение.
3. Если определить победителя невозможно, программа должна сообщить о конфликте и не изменять спорный участок без подтверждения пользователя.

Пример:

```text
Строка:
Authorization: Bearer abcdef123456

Обнаружены совпадения:

- правило token: Bearer abcdef123456
- правило identifier: abcdef123456

Будет применено правило token,
поскольку оно имеет больший приоритет.
```

Порядок применения правил должен быть одинаковым при повторной обработке одного и того же файла одной и той же политикой.

# 6. Конфигурационный файл

Политики и общие настройки приложения должны храниться в отдельном конфигурационном файле.

Формат выбирается разработчиком. Например, JSON, YAML или TOML.

Пример конфигурации:

```json
{
  "logFile": "anonymizer.log",
  "reportDirectory": "reports",
  "outputDirectory": "anonymized",
  "defaultPolicy": "strict",
  "preserveDirectoryStructure": true,
  "overwriteExistingFiles": false,
  "supportedExtensions": [
    ".txt",
    ".log",
    ".json",
    ".csv",
    ".xml",
    ".md"
  ],

  "policies": {
    "personal-data": {
      "description": "Персональные данные",
      "rules": [
        {
          "id": "emails",
          "matcher": {
            "type": "builtin",
            "value": "email"
          },
          "replacement": {
            "type": "pseudonym",
            "template": "user{number}@example.com"
          },
          "priority": 100,
          "enabled": true
        },
        {
          "id": "phones",
          "matcher": {
            "type": "builtin",
            "value": "phone"
          },
          "replacement": {
            "type": "constant",
            "value": "[PHONE]"
          },
          "priority": 90,
          "enabled": true
        }
      ]
    },

    "credentials": {
      "description": "Пароли и токены",
      "rules": [
        {
          "id": "password-fields",
          "matcher": {
            "type": "regex",
            "value": "(?i)(password|passwd|pwd)\\s*[=:]\\s*\\S+"
          },
          "replacement": {
            "type": "constant",
            "value": "$1=[REDACTED]"
          },
          "priority": 200,
          "enabled": true
        }
      ]
    },

    "strict": {
      "description": "Полная очистка перед публикацией",
      "includes": [
        "personal-data",
        "credentials",
        "network-data"
      ],
      "rules": [
        {
          "id": "emails",
          "matcher": {
            "type": "builtin",
            "value": "email"
          },
          "replacement": {
            "type": "constant",
            "value": "[EMAIL]"
          },
          "priority": 150,
          "enabled": true
        }
      ]
    }
  }
}
```

Приведённая структура является примером.

Политики, созданные через меню приложения, должны сохраняться в конфигурационном файле и становиться доступными без изменения исходного кода.

# 7. Предварительный просмотр и обработка файлов

Программа должна работать как минимум с текстовыми файлами в кодировке UTF-8.

Пользователь должен иметь возможность выбрать:

* отдельный файл;
* несколько файлов;
* каталог;
* каталог со всеми вложенными каталогами.

При обработке каталога необходимо учитывать список допустимых расширений из конфигурации.

Перед созданием результата программа должна показать сводку:

```text
Политика: strict
Источник: C:\Reports
Файлов найдено: 18
Файлов будет обработано: 14
Файлов пропущено: 4

Обнаружено:

Адреса электронной почты: 27
Телефонные номера: 8
Пароли и токены: 4
IP-адреса: 15
Значения из словарей: 6
Конфликты правил: 1
```

Пользователь должен иметь возможность просмотреть подробности по выбранному файлу:

```text
Файл: application.log

Строка 18:
alexey.petrov@company.ru
→ [EMAIL]

Строка 42:
password=secret123
→ password=[REDACTED]
```

После подтверждения программа должна создать копии в выходном каталоге.

Исходные файлы изменяться не должны.

Если обрабатывается дерево каталогов и в конфигурации включено сохранение структуры, относительные пути должны воспроизводиться в выходном каталоге.

Пример:

```text
Исходный файл:
C:\Reports\2026\july\application.log

Результат:
C:\Reports\anonymized\2026\july\application.log
```

Выходной каталог не должен находиться внутри сканируемого каталога таким образом, чтобы программа повторно обрабатывала собственные результаты.

# 8. Отчёт и мониторинг

После завершения операции программа должна сформировать отчёт.

Отчёт должен содержать:

* использованную политику;
* список включённых политик;
* время начала и завершения;
* количество обработанных и пропущенных файлов;
* количество замен по каждому правилу;
* количество конфликтов;
* список файлов с ошибками;
* путь к созданным копиям.

Пример:

```text
Обработка завершена.

Политика: strict
Обработано файлов: 14
Пропущено файлов: 4
Создано замен: 60
Конфликтов: 1
Ошибок: 0

Результат сохранён:
C:\Reports\anonymized
```

Приложение также должно вести журнал своей работы.

В журнал необходимо записывать:

* запуск и завершение приложения;
* загрузку и проверку конфигурации;
* создание, изменение и удаление политик;
* составление политик;
* обнаруженные переопределения и циклические зависимости;
* начало и завершение анализа;
* количество найденных совпадений;
* начало и завершение обработки;
* количество успешно обработанных файлов;
* ошибки чтения и записи;
* неизвестные команды;
* внутренние ошибки приложения.

В журнал запрещено записывать:

* найденные конфиденциальные значения;
* фрагменты исходных документов;
* значения до и после замены;
* содержимое словарей;
* полный пользовательский ввод, если он может содержать конфиденциальные данные.

Допускается записывать идентификаторы правил, количество совпадений и относительные пути к файлам.

# 9. Проверка политик и обработка ошибок

Перед использованием программа должна проверить конфигурацию и все задействованные политики.

Необходимо обнаруживать как минимум следующие ошибки:

* политика с указанным именем отсутствует;
* политика по умолчанию отсутствует;
* идентификаторы правил внутри одной политики повторяются;
* составная политика включает несуществующую политику;
* обнаружена циклическая зависимость;
* регулярное выражение имеет неправильный формат;
* способ поиска не поддерживается;
* способ замены не поддерживается;
* для замены не указано необходимое значение или шаблон;
* приоритет не является числом;
* словарь отсутствует или не может быть прочитан;
* выходной каталог совпадает с исходным;
* конфигурационный файл имеет неправильный формат.

Приложение также должно корректно обрабатывать:

* неизвестную команду;
* отсутствие выбранной политики;
* отсутствие исходного файла или каталога;
* неподдерживаемое расширение;
* неизвестную или повреждённую кодировку;
* невозможность прочитать отдельный файл;
* невозможность создать результат;
* существование выходного файла;
* конфликт правил;
* изменение исходного файла во время обработки;
* невозможность сохранить изменённую конфигурацию;
* невозможность создать журнал или отчёт.

Ошибка отдельного файла не должна прекращать обработку остальных файлов.

Если часть файлов не обработана, итоговый результат должен быть помечен как неполный.

Пример:

```text
Не удалось обработать файл:

logs\archive.log

Причина: файл содержит данные
в неподдерживаемой кодировке.

Обработка остальных файлов продолжена.
```

При неудачной перезагрузке конфигурации приложение должно продолжить использовать последнюю корректную версию.

# 10. Ограничения задания

В рамках лабораторной работы не требуется:

* гарантировать полную анонимность полученных документов;
* автоматически распознавать любые персональные данные;
* использовать нейронные сети;
* выполнять семантический анализ текста;
* обрабатывать изображения, аудио и видео;
* изменять исходные файлы;
* восстанавливать исходные значения по псевдонимам;
* обрабатывать архивы;
* работать с офисными форматами DOCX, XLSX и PDF;
* обращаться к внешним сервисам;
* загружать документы в интернет;
* шифровать исходные или результирующие файлы;
* создавать графический интерфейс.

Приложение решает задачу применения управляемых и составных политик анонимизации к текстовым файлам.

Результат необходимо считать подготовленной или обезличенной копией, но не доказательством невозможности повторной идентификации данных.
